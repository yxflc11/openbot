## 仓库现状

规范基线已合并跨平台员工与可移植性切片。仓库证据确认 Server 管理的员工档案、经审查技能、
类型化记忆、演进事件、员工包审查/导入、单 Node 登记与吊销、带版本的 Provider 能力路由、
有界实时传输、产物校验、迁移漂移检查和有界停机均已存在。未修改基线通过文档、研究与迁移清单
检查；新工作树尚未安装依赖，因此完整基线检查到 lint 时因 `biome: command not found` 中止，
不能把它记为仓库测试失败。

同一批证据也表明产品仍为 pre-alpha。Cua、Lume、Coder 只有声明；原生桌面 Provider、持有证明
身份、能力租约、加固的浏览器出站边界、系统密钥库、连续接管、可执行技能扫描、注册表分发、
所有权转移和可选办公室插件生命周期均不是生产能力。

## 修复顺序与安全契约

1. H1：Server 在持久化前重新计算策略和最低风险；未知 action 默认拒绝，并拒绝 Node 降低风险。
2. H4：登录限速必须原子且持久；默认使用直连 peer 身份，只信任显式配置代理发来的转发元数据。
3. M3：增加固定版本、只读的生产依赖与 secret 扫描 CI。
4. M1、M6、M7、L5：复用客户端身份与结构化错误/日志边界，不能另造平行信任规则。
5. H2、H3、M2、M5：只有完整的 fail-closed 协议或平台设计后才能继续。当前明确披露并限制为
   disabled/development 比不可验证的半成品控制更安全。

每项行为修复都必须先完成研究记录并更新复用台账。DEV-001 关闭前，本审计还必须补充提交、准确测试、
剩余风险和最终验证输出。
