## 修复顺序与安全契约

1. H1：Server 在持久化前重新计算策略和最低风险；未知 action 默认拒绝，并拒绝 Node 降低风险。
2. H4：登录限速必须原子且持久；默认使用直连 peer 身份，只信任显式配置代理发来的转发元数据。
3. M3：增加固定版本、只读的生产依赖与 secret 扫描 CI。
4. M1、M6、M7、L5：复用客户端身份与结构化错误/日志边界，不能另造平行信任规则。
5. H2、H3、M2、M5：只有完整的 fail-closed 协议或平台设计后才能继续。当前明确披露并限制为
   disabled/development 比不可验证的半成品控制更安全。

## 剩余风险与明确延后

- H2：尚无签名、TTL 绑定、单次消费 capability lease；真实副作用 Provider 继续禁用。
- H3/M1：尽管已有单次登记、单 Node 吊销、安全文件、限速与假名审计，Node 启动凭证仍可复制。
  PoP、轮换、mTLS 与系统钥匙串属于后续协议/平台工作。
- M2：在浏览器真实连接处强制重定向与 DNS/连接策略前，出站不是可执行的 SSRF 边界。
- M5：获得原生 ACL/钥匙串和真实 Windows 证据前，Windows 凭证保护仍为 Development。
- L3/L4：应用秘密启发式刻意不完整；离线泄露密码筛查需要另行审查隐私与更新生命周期。
- 本地结构化日志没有增加远程 telemetry、保留、告警路由或分布式 tracing；多 Server 事件/队列设计
  也不在 DEV-001 范围内。
