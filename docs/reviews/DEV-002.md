## Remaining risks and next work

The image has passed the named hosted checks but has not been published or promoted to a platform
support level. `/health` is liveness after startup, not ongoing database readiness. Startup signals,
busy dispatcher drains, and stalled database close still lack full lifecycle evidence. Existing
root-owned object volumes need an operator-reviewed migration. Compose's raw database password
interpolation needs a separately tested encoding change. PostgreSQL digest pinning, image OS
vulnerability scanning, release SBOM/provenance, backup/restore and upgrade/rollback acceptance are
still release work.

Using the existing [G0–G10 acceptance plan](../EXECUTION_PLAN.md), G0 and G1 are complete at their
stated evidence levels. **Nine gates remain: G2–G10.** G2–G5 have partial implementations but still
need Provider-specific scenarios and controlled device/install/keyring evidence; G6–G10 cover
device proof of possession, executable Skill containment, governed retrieval/proposals,
distribution/ownership, and real computer control. G11 remains deliberately deferred. The gates
have very different sizes, so this count is not a percentage of product completion.

The recommended next implementation is G2's bounded Docker/browser conformance suite: use only a
loopback fixture service, run the existing adapter through the existing conformance runner, cover
authentication failure, navigation/screenshot bounds, malformed responses, cancellation and
cleanup, emit a strict hermetic report, and make CI fail on required scenario failures. Reuse the
already-reviewed runner and upstream adapter contracts before adding behavior. A fixture-backed
pass must remain hermetic evidence; it does not prove a real browser or desktop platform. This
optional follow-on is not implemented or claimed complete by the Server container PR.
